# 简历项目描述与面试准备

所有数字限定于当前可核验的实现和历史实验，不代表通用 benchmark 或线上生产指标。仓库：[research-rag-agent](https://github.com/cldw1/research-rag-agent)。

## 中文项目介绍

独立开发面向英文科研论文的 Research RAG Agent，支持 QASPER Validation 论文选择与本地 PDF 上传问答。实现 BM25 与 BGE/FAISS 混合检索、RRF 融合、Anchor-First 证据扩展，通过 DeepSeek Tool Calling 自主选择论文目录和正文搜索工具；提供工具调用记录、稳定数字引用、页码与 Chunk 原文追踪。针对特定 HMC PDF 实现受校验保护的 V3 章节映射与可选章节重排序，并通过离线回归测试和小样本检索评估验证功能与边界。

## 可用于简历的四条经历

- 使用 Python、Streamlit 构建科研论文问答原型，接入 QASPER Validation 与文本型 PDF，完成解析、分块、索引、检索、生成和原文引用展示流程；限制上传大小、页数及 Chunk 数量，处理无文本与缺失索引等异常。
- 实现 BM25 + BGE-small-en-v1.5 + FAISS Hybrid Retrieval，通过 RRF 融合排名，并以 Anchor-First 在字符预算内组织完整证据，减少邻居扩展挤占核心检索片段的问题。
- 基于 DeepSeek Tool Calling 实现论文目录与正文搜索工具，加入论文范围校验、每题/会话工具调用预算，以及基于 `(paper_id, chunk_id)` 的引用注册与去重；通过策略代理连接 Agent 与可切换检索策略。
- 在单篇 HMC 论文的 7 道章节级问题上比较 Hybrid 与 Section-Aware：Hit@5 从 85.7% 到 100%，MRR@5 从 0.786 到 0.929，人工证据充分率均为 85.7%；保留 Hybrid 为默认，并明确小样本、暂定标签及单评审限制。

简历篇幅有限时可保留前三条，在最后一条中简述检索评估；不要使用「问答准确率达到 100%」「通用性能提升」「生产级高并发」等缺少证据的表述。

## 面试追问与回答思路

**为什么同时用 BM25 与 Dense？为什么用 RRF？**

BM25 更直接利用术语和关键词，Dense 捕捉语义相近表达；两路分数尺度不同，RRF 只依赖名次，工程实现简单。项目实现了融合，不应在没有相应大规模消融时声称每一组件都带来了稳定提升。

**FAISS 中为什么使用 IndexFlatIP？**

正文和查询均归一化后，内积相当于余弦相似度；当前单论文规模较小，精确索引便于验证。若扩展到大量文档，可测量内存和延迟后比较 ANN 索引，当前没有相关吞吐实测。

**普通 PDF 与 V3 章节感知有什么区别？**

普通 PDF 的 `Page X` 是页码标签；HMC V3 使用特定文件的已验证章节定位映射，应用同时检查文件名、SHA256 和映射可用性。不能将它描述为对任意 PDF 都有效的章节检测器。策略代理禁止未验证索引使用 Section-Aware。

**Section-Aware 会不会只是在针对测试集调规则？**

规则来自开发阶段的章节实验，当前七题仍只覆盖同一论文，不能排除结构特定的偏差。报告披露参数、扩大候选池、逐题结果与暂定标签；后续应固定版本，在跨论文且未参与开发的人工核验集上评估。

**为什么 Hit@5 提升而人工证据充分率没有提升？**

命中章节只意味着某个 Chunk 来自正确章节，未必包含问题所需条件、公式或完整解释。H03 的证据改善，但 H07 的人工分下降，二者抵消。这也解释了为何保留 Hybrid 默认，避免只看一个指标。

**Anchor-First 和 SmartSection 解决什么问题？**

先保留原始检索证据，再补相邻文本，降低上下文碎片化。普通扩展按同章节索引/页码的邻段查找；已验证 V3 的 Section-Aware 才启用跨页同真实章节候选，结合关键词、距离和公式编号排序，并在预算足够时最多补两块。它是启发式规则，仍有漏检风险。

**怎样证明 Agent 真正接入所选策略？**

将 `RetrievalStrategyProxy` 作为原检索器接口传入 Agent，搜索工具复用 RAG Pipeline，最终拦截 `search()`；记录每轮代理调用增量。离线测试调用真实的 Agent 工具执行与 Pipeline，模型响应使用模拟对象，不产生费用。真实 API 运行证据与离线回归的作用需要区分。

**数字引用能否保证回答可信？**

全局注册表保证编号稳定、去重和可追溯，校验不存在的编号并展示原文；不能证明句子被原文语义支持。还需答案忠实度、引用精确率/覆盖率和人工评审。系统提示检索文本是数据，但不宣称已经彻底解决提示注入。

**上下文限制如何实现？**

字符预算包含每个证据块的标题、论文与 Chunk 元数据、引用编号和分隔符；完整块依次放入，不截断原文。预算不足时减少块，连首块都无法放入时明确报错。字符数不是 token 数，也不是完整会话上下文窗口管理。

**工程上还有什么不足？**

当前上传索引仅在会话内保存、没有持久化或跨用户协作；没有生产并发压测、通用章节识别、OCR 或可靠公式结构化。下一步优先补跨论文评估和语义忠实度检验，再依据延迟和资源测量决定扩展方案。
